The arrows represent internal runtime dependencies from the child to the
ancestor/additions. +tool/check_package_topology.dart+ checks the exact
allowlist, rejects cycles, and proves that core has no package imports while
sync and modeling import only core. Analyzer, formatting, CLI, and generation
remain host tooling and never enter an application runtime graph.

Public entrypoints:

* +package:dartitect/dartitect.dart+
* +package:dartitect_modeling/dartitect_modeling.dart+
* +package:dartitect_modeling_analyzer/dartitect_modeling_analyzer.dart+
* +package:dartitect_sync/dartitect_sync.dart+
* +package:dartitect_isolates/dartitect_isolates.dart+
* +package:dartitect_flutter/dartitect_flutter.dart+
* +package:dartitect_flutter/dartitect_flutter_reactive.dart+
* one same-named entrypoint for observability, Dio, Drift, ObjectBox, Sentry, testing,
  privacy, media, locale BR, geometry, CLI, lints, and MCP.

There is no umbrella or Material entrypoint. Applications render headless
reactive state with their own Material, Cupertino, or design-system widgets.
MCP is retained only for local host tooling and never becomes an application
dependency.

== Dependency direction

View -> ViewModel -> application/domain contract -> infrastructure
implementation. Only explicit composition roots see the complete graph.
Generated entities/DTOs, provider clients, databases, Stores, credentials, telemetry
destinations, conflict policy, schema, and UI effects remain consumer-owned.
Every isolate constructs a new graph and transfers values/envelopes only.

== Platform boundaries

Core, modeling, sync, isolates, observability, locale BR, and geometry are pure Dart.
Flutter APIs stay in +dartitect_flutter+; privacy is iOS-only and media supports
Android/iOS through narrow platform channels. Drift is executor-neutral across
native and web, while ObjectBox is native-only and keeps its Store local to one
isolate. The modeling analyzer, CLI, lints, and MCP are host tools. Dio and
Sentry are opt-in adapters.

The machine inventory in +tool/sdk_inventory.json+ records each reviewed
package, version, internal dependency, entrypoint, public-symbol count, and
keep/add/remove decision.

== Publication layers

The dependency DAG is also the release order. Independent roots publish first;
modeling follows core, the shared compiler follows modeling, CLI/lints follow
the compiler, and MCP follows CLI. Adapters publish only after all runtime
dependencies are available. The exact deterministic
order and lockstep constraint are checked from
+tool/package_release_contract.json+; directory/alphabetical order is not a
publication contract.
