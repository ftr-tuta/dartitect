= Getting started

Start with a new Dartitect project. There is no conversion, gradual adoption,
legacy zone, or competing-runtime mode. Keep domain contracts free of
Dartitect types when ordinary Dart types suffice.

The normal application entrypoint delegates ownership to the generated graph:

[source,dart]
----
void main() => runDartitectApplication<ApplicationGraph>(
  create: ApplicationModule.create,
  application: (graph) => OrdersApp(graph: graph),
);
----

At a route boundary, render the generated `<Feature>FeatureHost`. Supply the
typed factory and exhaustive loading/failure/ready builders; the host creates
and starts the ViewModel, fences late work, and closes the ViewModel before the
feature graph. Use `CommandStateBuilder` inside product UI when all six command
states need exhaustive rendering. Neither widget chooses Material, text,
layout, navigation, colors, or style.

Manual `ResourceOwner`, `OwnedGraph`, `DartitectAssemblyBinding`,
`BootstrapCoordinator`, and `ViewModelHost` composition remains documented in
link:composition-lifecycle-isolates.md[the advanced lifecycle guide].

Create only the requested platforms, review config v3, and preview every
generated change:

[source,shell]
----
dart run dartitect_cli:dartitect create app orders_app --targets=android,web
cd orders_app
dart run dartitect_cli:dartitect scan --json
dart run dartitect_cli:dartitect doctor
dart run dartitect_cli:dartitect create feature orders \
  --profile=local --scope=application --targets=android,web --dry-run
----

Generated-once files belong to the consumer immediately. A conflicting file is
never overwritten and there is no `--force` flag.
