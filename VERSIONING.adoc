= Versioning and publication policy

== One lockstep 1.0.x cohort

All 16 publishable packages use one version for every development, RC, and
stable release. +dartitect_mcp+ is host-only tooling but remains part of the
same version and publication cohort. A release with a missing package, a mixed
version, or a changelog whose first release heading differs from the cohort is
invalid.

Public Dart APIs follow Semantic Versioning. JSON output has its own
+schemaVersion+ and configuration has +configVersion+; package compatibility
never implies persisted-schema compatibility. A public API deprecation remains
for at least one minor release and documents its replacement.

[cols="2,2,3,3",options="header"]
|===
| Stage | Package version | Required internal constraint | Supported consumer graph

| Development
| +1.0.0-dev.N+
| +>=1.0.0-dev.N <1.0.0+
| Local/packaged validation only; all resolved Dartitect packages use the exact
  same development cohort.

| Release candidate
| +1.0.0-rc.N+
| +>=1.0.0-rc.N <1.0.0+
| Materialized RC validation only; mixing RC numbers, development, or stable is
  unsupported.

| Stable 1.0 patch
| +1.0.P+
| +>=1.0.P <1.1.0+
| Every explicitly selected Dartitect package should use the same released
  patch. The lower bound prevents a dependent package from resolving an older
  internal package; the minor ceiling prevents accidental 1.1 mixing.
|===

Independent leaf packages cannot enforce cohort equality through pub
constraints because they do not depend on one another. Installed canaries must
therefore inspect +package_config+ and the lockfile and reject a mixed
Dartitect graph explicitly.

The 1.0 SDK floor is Dart 3.13.0. Flutter packages additionally require Flutter
3.47.1. A monorepo +path:+ dependency or workspace-only resolution is never
evidence that a distributable consumer can resolve. The protected Git candidate
is the one explicit exception for dependency overrides: every selected and
transitive Dartitect package must use the same remote URL and annotated tag,
and the lockfile must prove one peeled commit. Those overrides are Git-
consumption evidence only; they do not authorize or simulate pub.dev
publication.

== Protected Git candidate

+v1.0.0-rc.2+ is annotated, unsigned, and protected against update/deletion.
It exposes only the repository tree; it has no GitHub Release and no pub.dev
publication. +tool/git_dependency_overrides.dart+ computes the internal closure
for any package combination, while +tool/run_git_canaries.dart+ validates the
minimal, offline-first, and native consumers against a supplied remote/tag.

The prior +v1.0.0-rc.1+ tag remains an immutable protected historical
candidate. RC.2 never moves, deletes, or reuses that ref.

This consumption tag is distinct from the future formal signed channel. Formal
readiness, signatures, hosted archives, and package publication retain their
separate authorization and evidence requirements.

== Generated-file compatibility

Generated-once files belong to the consumer and are never rewritten by an SDK
upgrade. Fully generated files require the identifying header, exact generator
version, input schema, and manifest ownership. Managed sections are not used in
1.0. Unknown manifest, journal, report, or configuration schemas fail closed;
schema migration is always explicit.

== Publication DAG

Publication is manual and strictly follows these dependency layers. Packages
inside a layer have no internal dependency on each other; the reviewed order
inside each layer is deterministic even when the channel could accept parallel
uploads.

. Layer 0: +dartitect+, +dartitect_cli+, +dartitect_geometry+,
  +dartitect_lints+, +dartitect_locale_br+, +dartitect_privacy+.
. Layer 1: +dartitect_flutter+, +dartitect_isolates+, +dartitect_mcp+,
  +dartitect_media+, +dartitect_observability+, +dartitect_sync+.
. Layer 2: +dartitect_dio+, +dartitect_objectbox+, +dartitect_sentry+,
  +dartitect_testing+.

+tool/package_release_contract.json+ is the machine authority for the cohort,
constraints, layers, exact order, artifact requirements, and partial-failure
policy. +tool/check_package_release_contract.dart+ rejects drift. The release
audit runs publish dry-runs in that exact order, not directory order.

== Reproducible release evidence

Every formally materialized hosted/bundle cohort is tied to one exact +main+
SHA and starts from a clean clone with a clean tracked tree. It contains no
dependency overrides or path dependencies. CI, Security, API review,
SBOM/license/advisory checks,
Dartdoc, clean-clone canaries, and all 16 publish dry-runs refer to the same
source SHA.

For every package, record the cohort version, order index, sorted file
inventory, canonical SHA-256 source digest, channel/archive SHA-256, SBOM hash,
source SHA, SDK versions, command, timestamp, and result. Canonical source
digests hash sorted relative paths and file bytes and do not depend on archive
timestamps. A signed bundle additionally records the signature/provenance.
Rebuilding in a second clean directory must reproduce the canonical source
digests before a release decision.

Generated examples, provider outputs, package metadata, changelogs, license
files, and manifests are part of the reviewed source inventory. Credentials,
local paths, build outputs, private plans, caches, and transaction residue are
forbidden.

== Partial publication recovery

pub.dev does not provide a 16-package atomic transaction and published versions
cannot be overwritten. Materialization therefore uses an append-only receipt
ledger and stops at the first ambiguous or failed upload.

. Query the channel for the exact package/version; never infer success from a
  timed-out client.
. If the exact version exists and its channel/archive digest matches the
  authorized artifact, record it as verified and resume with the next package.
. If it does not exist, retry only the same package from the same source SHA and
  identical digests after an explicit resume decision. There is no automatic
  publish retry.
. Never republish or mutate a successful package and never skip a failed
  dependency to publish its dependents.
. If any remaining artifact, source, dependency, or documentation must change,
  abandon the unfinished cohort, preserve all receipts, create the next
  development/RC/patch cohort for all 16 packages, and rerun every gate.
. A digest mismatch or an unexpected package already present is a security
  incident and blocks the channel until reconciled.

An abandoned partial cohort is never called an RC or stable release. Already
published immutable packages remain visible as historical artifacts; release
notes and receipts state that the cohort is incomplete and superseded.

== Authorization boundaries

Green local gates do not authorize a formal signed tag or publication. The
separately authorized Git-consumption tag grants neither. V1S-15 requires a
delegated review-authority +READY_FOR_1_0_RC+ decision for one exact +main+ SHA
and a separately selected RC channel. V1S-16 materializes only that channel.
V1S-17 validates installed artifacts and records +READY_FOR_1_0+. Stable V1-18
uses a new SHA, a release-only diff from the final RC, repeated gates, and a
separate delegated review-authority publication decision.
